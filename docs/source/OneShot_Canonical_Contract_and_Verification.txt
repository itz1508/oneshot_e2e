# OneShot Canonical Contract & Verification Specification

## 1. Purpose

This specification completes the machine-readable definitions required by the OneShot workflow:

```text
Prompt_id
→ Researcher
→ Researcher(id)
→ Planner
→ audit_id
→ Refactor
→ plan_id
→ Gap Analysis
→ gap_0 + plan_id
→ Evaluation
→ plan_id
→ Triple Validation
   ├── Schema Validation
   ├── Fixture Validation
   └── Goal Validation
→ CONFIRMED
→ CREATE HASH
→ HASH
→ DONE
```

It defines:

1. Canonical JSON Schema files and fields
2. `Researcher(id)`
3. `audit_id`
4. Gap records and `gap_0`
5. Evaluation evidence and output
6. `validation_id`
7. Confirmed package
8. Canonicalization bytes
9. Hash creation and verification
10. Machine-readable workflow graph
11. Contract registry and contract identity
12. Concrete E2E fixtures

# 2. Canonical Contract Directory

```text
schema/
├── common.schema.json
├── researcher.schema.json
├── plan.schema.json
├── schema-artifact.schema.json
├── fixture.schema.json
├── goal.schema.json
├── validation.schema.json
├── audit.schema.json
├── gap.schema.json
├── evaluation.schema.json
├── triple-validation.schema.json
├── confirmed-package.schema.json
├── hash-proof.schema.json
├── workflow-graph.schema.json
└── contract-registry.schema.json
```

All schemas use JSON Schema Draft 2020-12.

Canonical contract identity uses URN identifiers:

```text
urn:oneshot:schema:<contract-name>:<version>
```

Example:

```text
urn:oneshot:schema:researcher:1
```

# 11. Gap Record

Gap Analysis identifies and repairs concrete missing or incomplete portions of the plan.

## Gap record

```text
gap
├── gap_id
├── plan_id
├── affected_branch
├── issue
├── evidence_ids
├── required_correction
├── expected_resolved_state
└── resolution_evidence
```

## Gap Analysis output

```text
plan_id
+
resolved_gaps[]
+
gap_0 = true
```

`gap_0 = true` means the fresh recheck found zero remaining identified gaps.

# 15. Canonicalization Byte Algorithm

Canonicalization identity:

```text
oneshot-jcs-rfc8785-v1
```

Hash identity:

```text
sha256
```

Combined proof identity:

```text
oneshot-jcs-rfc8785-sha256-v1
```

## Exact operation

Input:

```text
confirmed_package.core
```

Processing:

```text
1. Validate confirmed_package.
2. Extract confirmed_package.core.
3. Parse the core as JSON data.
4. Canonicalize the JSON value using RFC 8785 JCS.
5. Use the exact UTF-8 byte sequence emitted by JCS.
6. Compute SHA-256 over those bytes.
7. Encode the digest as lowercase hexadecimal.
```

Formally:

```text
canonical_bytes =
    JCS_RFC8785(confirmed_package.core)

HASH =
    HEX_LOWER(
        SHA256(canonical_bytes)
    )
```

No timestamp, runtime status, filesystem path, checkpoint state, execution environment metadata, or packaging metadata participates in the comparable representation.

The comparable object is:

```text
confirmed_package.core
```

The exact same object definition is used during creation and later verification.

# 16. Reference Python Hash Interface

```python
from __future__ import annotations

import hashlib
from typing import Any, Protocol


class JCSCanonicalizer(Protocol):
    def canonicalize(self, value: Any) -> bytes:
        ...


def create_hash(
    confirmed_core: dict,
    canonicalizer: JCSCanonicalizer,
) -> str:
    canonical_bytes = canonicalizer.canonicalize(confirmed_core)

    return hashlib.sha256(
        canonical_bytes
    ).hexdigest()


def verify_hash(
    confirmed_core: dict,
    expected_hash: str,
    canonicalizer: JCSCanonicalizer,
) -> bool:
    actual_hash = create_hash(
        confirmed_core=confirmed_core,
        canonicalizer=canonicalizer,
    )

    return actual_hash == expected_hash
```

The `JCSCanonicalizer` implementation follows RFC 8785 exactly.

This keeps the hash implementation independent from the library selected to perform JCS serialization.
